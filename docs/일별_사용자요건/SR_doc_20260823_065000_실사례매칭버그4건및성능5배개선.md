## 반영 내용

### 1. 실데이터 정성 감사(proactive audit) — "매핑이 개판" 지적 검증 (원문 1)

실제 6개 마켓 캐시 데이터(`data/market_categories_cache.json`, 14,882건)
로 12개 대표 필터명을 직접 돌려 결과를 전수 검토했다. 이 과정에서
사용자가 이어서 던진 "여성-신발"·"여성-신발-구두" 두 질문(원문 3·4)에
답하려고 실제 코드를 추적하다가, 아래 4가지 **실제 오매핑 버그**를
발견해 전부 수정했다.

| 버그 | 실사례 | 원인 | 수정 |
|------|--------|------|------|
| a) 최상위 텍스트 오염 | "남성-속옷-드로즈" → "패션잡화 > 남성화"(신발) | `path_class` 가 최상위 "의류/언더웨어"의 "의류" 글자로 오분류 | 최상위 제외하고 먼저 판정, 안 되면만 포함해 재시도 |
| b) 무표기 후보 하드배제 | "남성-신발-스니커즈" → "남성샌들 > 아쿠아슈즈" | `gender_paths` 가 같은 성별 표기 있으면 무표기 후보를 통째로 배제 | 반대 성별만 배제, 같은 성별 우선은 점수(`priority_rank`)로 |
| c) 용어차(구두↔단화) | "여성-신발-구두" 검색이 0건(마켓상 여성 쪽은 "단화") | 사전에 없음 | `구두`↔`단화` 동의어 등록 |
| d) 비제품(건강·관리용품) 오분류 | "남성-악세서리-목걸이" → "건강목걸이" | 목걸이라는 글자만 보고 액세서리로 분류 | `NON_PRODUCT_HINT_WORDS`(건강·관리용품·케어 등) 신설, 대안 있으면 배제 |

수정 후 12개 필터명을 6개 마켓 전체(72건)로 재검증 — 전부 명확히
개선(정확한 품목 카테고리로 확정)됨을 확인했다.

### 2. 성능 5배 개선 (원문 5·6·7·8)

"시간 질질 끄냐"는 지적에 실측했더니 `find_category` 1회 호출에
**마켓당 평균 500ms**(6개 마켓·행 1개면 약 3초)가 걸리고 있었다.
`cProfile` 로 원인을 추적해 4곳을 고쳤다.

| 원인 | 문제 | 수정 |
|------|------|------|
| `KeywordDB.leaves()`/`is_leaf()` | 카테고리마다 전체를 다시 훑는 O(N²) — 14,000여 건에서 1회 호출 4초 | 부모→자식 색인(`_children`)으로 O(1)/O(N) |
| `KeywordDB.lookup()`/`resolve()` | 검색어 20만 건을 매번 선형 탐색 | `_keyword_index`·`_leaf_name_index` 사전 색인 |
| `class_of` | 후보 경로마다 계열 단어 전부를 매번 `normalize` | 모듈 로드 시 1회만 정규화(`_CLASS_WORDS_NORM`) |
| `_specific_item_conflict` | 경로 텍스트·단어 목록을 매번 재정규화 + `expand_synonyms([parsed.mid,*parsed.lows])` 를 경로마다(값이 항상 같은데도) 재계산 | 정적 단어 사전 사전정규화, `wanted` 를 호출부에서 1회 계산해 재사용 |

결과: **마켓당 평균 500ms → 100ms (5배)**, `keyword_db` 구축
4.3초 → 0.36초. 성능 회귀 방지 테스트 3건 추가(2,000개 카테고리
기준 구축 2초 이내·`leaves()` 50회 1초 이내·`resolve()` 200회
0.5초 이내).
